# Tapeek 执行 Tickets：索引与工作流

## 1. 使用方式

每个 ticket 是一个独立工作单元，按依赖顺序执行。执行者先读本页，再读 ticket、PRD 对应章节、规格对应章节和 [实施计划](../impl-plan.md) 第 9 节的 Core 契约。

不要按本文一次性实现全部功能。不要跳过前置 ticket 直接做 UI。不要在一个 ticket 中顺手重构其他模块。

## 2. 状态

| 状态 | 含义 |
| --- | --- |
| 待开始 | 尚未修改任何文件 |
| 进行中 | 已开始，有明确的下一个动作 |
| 阻塞 | 缺少用户决定、签名、系统权限或前置产物 |
| 完成 | 验收项全部有证据，且 `docs/verification/Txx.md` 已填写 |

只有「完成」需要证据；「进行中」和「阻塞」也必须写入当前状态和阻塞原因。

## 5. 每个 Ticket 的结构

所有 ticket 使用统一结构：

- **元数据**：ID、状态、依赖、执行角色、审阅角色。
- **必读**：PRD、规格、契约的具体章节。
- **目标**：一句话说明完成后的可见结果。
- **允许改动**：白名单；越界即停止。
- **禁止改动**：常见越界点。
- **前置检查**：开始前必须确认的环境或产物。
- **步骤**：按顺序执行，每步有可观察结果。
- **验收**：命令、用例编号、预期。
- **证据**：写入哪个文件、需要哪些截图或输出。
- **停止条件**：何时必须停下来求助，而不是继续猜。
- **交接**：给下一个 ticket 的输入。

## 6. 执行角色

| 角色 | 适合的工作 |
| --- | --- |
| thinker | 读规格、拆分、审查接口、判断失败原因、写决策记录 |
| executor | 按 ticket 写代码、跑命令、补测试、截图、填写证据 |

一个 ticket 可以由同一个 agent 完成，也可以先由 thinker 审阅方案，再由 executor 实施。不要让 executor 自行改变需求或扩大范围。

## 7. 低能力执行者的约束

给执行 agent 的指令必须包含：

1. 只读本 ticket 列出的文件，不要浏览整个仓库后自行发挥。
2. 先运行前置检查；失败就停，不要猜环境。
3. 每次只改一个模块；改完立即编译或跑测试。
4. 命令失败两次就停，记录完整错误，不重复第三次相同命令。
5. 不安装新工具、不改系统设置、不使用 `sudo`、不停用其他 App 的扩展。
6. 不把「编译通过」当成「功能通过」；必须跑 ticket 指定的验收命令。
7. 证据只写实际输出；没有运行的项目写「未验证」。
8. 完成后按交接模板汇报，不写长篇总结。

## 8. 交接模板

```markdown
## Txx 交接

- 状态：完成 / 部分完成 / 阻塞
- 改动文件：
  - path
- 已运行命令与结果：
  - `command` → 退出码，关键输出
- 已通过验收：
  - ID
- 未通过或未验证：
  - ID，原因
- 给下一个 ticket 的输入：
  - 可复用的类型、脚本、样本
- 需要用户决定：
  - 无 / 具体问题
```

## 9. 变更规则

- 修改 ticket 的范围、依赖或验收项，必须先更新本页和对应 ticket，再实施。
- 发现规格矛盾时，记录到 ticket 的「阻塞」部分，由协调者决定；执行者不要自行选一个解释继续。
- 新增功能不塞进现有 ticket；新建 ticket 并更新依赖图。
- 完成一个 ticket 后，只把它标记为完成，不顺带把下一个 ticket 标记为完成。
