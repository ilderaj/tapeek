## 2. 编号

| 前缀 | 含义 | 示例 |
| --- | --- | --- |
| `MD-###` | Markdown 行为或验收用例 | `MD-012` |
| `ZIP-###` | ZIP 行为或验收用例 | `ZIP-021` |
| `QL-###` | Quick Look 集成行为 | `QL-005` |
| `APP-###` | 宿主 App 行为 | `APP-003` |
| `TEST-###` | 测试或夹具要求 | `TEST-008` |

编号一旦分配，不在后续文档中重复使用不同含义。删除的行为保留编号并标记「已废弃」，避免 ticket 与测试引用错位。

## 3. 规范用语

- **必须**：不满足即验收失败。
- **应该**：默认这样做；偏离时必须在验收记录中说明理由。
- **可以**：允许的实现选择，不影响通过。
- **不做**：明确排除，不在本版本实现。

## 4. 共同基准

- 目标系统：macOS 27.x，arm64。
- 界面语言：简体中文；代码标识符、文件名、路径保持原文。
- 外观：跟随系统浅色/深色，不提供独立主题开关。
- 数据：只读、本地处理、不联网、不写入用户文件。
- 失败：必须可见，不允许空白页、无限加载或静默截断。
- 限额：沿用 `PreviewLimits.default`；数值变更必须同时更新 PRD、规格、测试和验收记录。

## 5. 验收用例写法

每个用例包含：

| 字段 | 说明 |
| --- | --- |
| ID | 稳定编号 |
| 前置 | 样本、设置或系统状态 |
| 操作 | 用户或脚本动作 |
| 预期 | 可观察的结果 |
| 证据 | 截图、命令输出或测试名 |

用例的预期必须能被另一个执行者独立判断。避免「显示正常」「体验良好」这类无法复核的描述。

## 7. 变更规则

- 修改行为先改规格，再改代码和测试；三者同一次交付。
- 新增边界情况时，先判断它是否在 MVP 范围内。超出范围的内容写入「不做」或后续规划，不临时扩张。
- 任何被系统能力限制的行为（例如相对图片不可读）都必须写成明确的降级表现，而不是留空。
